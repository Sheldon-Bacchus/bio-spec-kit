# 任务：[FEATURE NAME]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**前置条件**：`plan.md`（必需）、`spec.md`（用户故事必需）、`research.md`、`data-model.md`、`contracts/`

**测试**：下面包含测试任务示例。只有功能规格说明明确要求时，才加入测试任务。

**组织方式**：按用户故事分组任务，以支持独立实施和独立测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可以并行运行（使用不同文件，且不存在依赖）
- **[Story]**：任务所属的用户故事（例如 US1、US2、US3）
- 描述中包含准确的文件路径

## 路径约定

- **单项目**：仓库根目录下的 `src/`、`tests/`
- **Web 应用**：`backend/src/`、`frontend/src/`
- **移动端**：`api/src/`、`ios/src/` 或 `android/src/`
- 下面的路径默认采用单项目结构；请根据 `plan.md` 调整

## 依赖关系与执行顺序

### 阶段依赖

- **Setup（Phase 1）**：无依赖——可以立即开始
- **Foundational（Phase 2）**：依赖 Setup 完成——阻塞所有用户故事
- **用户故事（Phase 3+）**：全部依赖 Foundational 阶段完成
  - 如果人员充足，随后可以并行；
  - 或按照优先级顺序（P1 → P2 → P3）依次执行。
- **Polish（最终阶段）**：依赖所有目标用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：Phase 2 后开始——不依赖其他故事
- **用户故事 2（P2）**：Phase 2 后开始——可能集成 US1，但应当可以独立测试
- **用户故事 3（P3）**：Phase 2 后开始——可能集成 US1/US2，但应当可以独立测试

### 每个用户故事内部

- 如包含测试，测试 MUST 先编写并确认失败；
- 模型先于服务；
- 服务先于 endpoint；
- 核心实施先于集成；
- 一个故事完成后再进入下一个优先级。

### 并行机会

- 所有标记 `[P]` 的 Setup 任务可以并行；
- Phase 2 中所有标记 `[P]` 的 Foundational 任务可以并行；
- Foundational 阶段完成后，所有用户故事都可以并行开始（如果团队容量允许）；
- 一个用户故事的所有标记 `[P]` 的测试可以并行；
- 一个故事中的模型可以并行；
- 不同用户故事可以由不同团队成员并行处理。

## 实施策略

### 优先 MVP（仅用户故事 1）

1. 完成 Phase 1：Setup；
2. 完成 Phase 2：Foundational（关键——阻塞所有故事）；
3. 完成 Phase 3：用户故事 1；
4. **停止并验证**：独立测试用户故事 1；
5. 如果准备好，则部署/演示。

### 增量交付

1. 完成 Setup + Foundational → 基础就绪；
2. 加入用户故事 1 → 独立测试 → 部署/演示（MVP）；
3. 加入用户故事 2 → 独立测试 → 部署/演示；
4. 加入用户故事 3 → 独立测试 → 部署/演示；
5. 每个故事都应当增加价值，同时不破坏之前的故事。

### 并行团队策略

多人协作时：

1. 团队共同完成 Setup + Foundational；
2. Foundational 完成后：
   - 开发者 A：用户故事 1；
   - 开发者 B：用户故事 2；
   - 开发者 C：用户故事 3。
3. 各故事独立完成并集成。

## 备注

- `[P]` 任务 = 使用不同文件，且不存在依赖；
- `[Story]` 标签将任务映射到具体用户故事；
- 每个用户故事都应当可以独立完成和测试；
- 实施前确认测试失败；
- 每个任务或逻辑分组完成后提交；
- 在检查点停下来，独立验证故事；
- 避免：模糊任务、同一文件冲突、破坏独立性的跨故事依赖。
